R1b plan (Claude, 2026-10-28): the embedding and stdlib inventory that gates the rnx default switch
(Commit this text as plans/R1b-embedding-inventory.txt in your plan commit; Rune and rnx records as usual: one plan + one impl each.)

WHY. R1 (2026-10-16) measured language-construct coverage but deferred three inventories that are REQUIRED before any engine switch: the stdlib registry, the host-function shapes, and the embedding API that rnx actually calls. After S5-S8 and W1, admitted programs behave exactly like legacy or refuse at compile time. What we don't yet know is which of rnx's REAL entry paths can route to the execution engine at all, and what falls back.

GOAL. A precise, reproducible answer to "if rnx routes every entry to the execution engine first (with compile-time fallback to legacy), what happens on each path?" It ends as a committed, live-checked table, not prose, and it becomes the design input for the rnx routing record.

STEP 0 (read-only; this IS most of the record; a decision point):
1. Embedding surface: every place rnx (src/, jupyter/, servers/, adapters/ including polars and candle, the session/REPL, `rnx run`, `rnx serve`, :dep assemblies) constructs and drives the legacy engine: Context and Module building, Sources/Diagnostics, prepare/build, Vm or Unit use, call/async/budget/fuel, globals, the RuntimeContext Arc, value conversion in and out, error rendering. For each call site: the execution-engine equivalent (exists / partial / missing), and what a default switch would need there.
2. Stdlib registry: every function, method and protocol in the default Context plus rnx's own modules, classified for the execution engine: certified and admitted / refused at compile time (with refusal kind) / not reachable. Weight it by actual usage in the 2,941 L1 programs, the 244 census programs, the rnx demos and the notebooks (counts from source, not stored outputs).
3. Host-function shapes: every rnx host registration's signature class (typed / dynamic with an output certificate / undeclared), and whether its argument and return shapes are importable.
4. Per entry path, the routing verdict: route-to-new (admits and is exact today), route-with-fallback (some programs refuse at compile time; fallback is safe), or blocked (no clean pre-execution refusal possible, for example async, generators, streaming servers or session state that spans compiles). Each blocked item names what it needs.
REPORT the table plus per-category percentages. Then I decide the routing record's scope with you: what routes at the switch, what stays legacy-only for now, and what must be built first.

IMPLEMENTATION (after the Step 0 ruling): make the table a committed, LIVE test, not a document. A test enumerates the registry and entry paths from code and asserts each row's verdict, so a future change that silently breaks routing fails. No stored outputs; counts are computed from committed sources. Any small, obvious gap the inventory exposes (a missing certificate on a typed host function, say) may be fixed in this record if it is tiny; otherwise list it for the routing record.

CONSTRAINTS. No change to legacy behavior. Product code changes only for those tiny gaps. Fresh-clone acceptance as rnxverify on strix. Counting: if R1b changes product code, it is product record #3 since M7, so M8 is DUE with it (the five cycle signals plus the alignment diagnostic). If it is inventory and tests only, it does not count, and M8 moves to the routing record.

RULING (chatd rune-r1b seq23601)
R1b Step 0: a superb inventory. Rulings:
(a) APPROVED: R1b is inventory plus live tests only, with no product certificate changes (process::exit, fs::metadata, time::parts and env::vars stay listed as candidates). R1b does not count toward M8. The routing record is product #3 since M7 and carries M8 (the five cycle signals plus the forced-alignment diagnostic).
(b) APPROVED: the routing scope is ONE-SHOT paths only. These route to the new engine with whole-program, compile-time legacy fallback: CLI single-file run; external-module and project-source-map runs (select legacy before effects where the loader is unsupported); `rnx project run` and generated assemblies; `rnx eval` (one input, fresh state); the config evaluator; and the Polars, Candle and PostgreSQL assembly file runs (their uncertified handlers and futures select legacy at compile time). The internal startup probe routes to the new engine. Persistent REPL/session, worker/Jupyter, `:dep` in a live session, every server API (Program/Invocation, Slot, `rnx serve`, http-postgres) and the selfcheck retained-Unit checks stay legacy-only. Your session counterexample is decisive: a cross-Program function value fails at RUN time after a mutation, so there is no safe fallback point. Those paths need their own design (session state, slices and cancel, a Bytes/Root bridge, async), as separate records after the switch. Never retry a runtime failure on legacy.
(c) APPROVED: the live-test design. Conditional registry rows with their source-form evidence; resolved vs lexically ambiguous source weights kept separate; the registry recomputed live from typed metadata via crate-private queries (no public introspection API, no stored dumps); rnx entry paths enumerated from committed source (AST/token-aware) and checked against per-path policy rows that ASSERT the blockers; the session counterexample and the pre-effect async and uncertified-host controls as live tests.
One addition for the routing record's plan (not R1b): the one-shot route must produce rnx-identical user-visible behavior: stdout/stderr, exit codes, the error rendering adapters (source maps, terminal escaping, bounds), budget semantics, and lifecycle. Its acceptance is a live dual-path comparison of the rnx CLI itself (legacy route vs new route) over the census, the demos and the L1 corpus, run as rnxverify.
